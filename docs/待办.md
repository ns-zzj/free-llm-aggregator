## ✅ 已做（2.0.0，2026-09-15）· 上游适配器 `openai-responses`

> **已完成**，实现方式比当初设想的更进一步：除了上游适配器，**下游也加了 Responses 方言**
> （`/openai/responses`），翻译逻辑统一放在 `src/protocol/responsesMapping.js`（两个方向一处实现）。
> 下面这段原始记录留档，说明当时的判断依据。测试见 `test/m10.test.js`（上游）与 `test/m12.test.js`（下游）。

**背景**：OpenAI 2025-03 起主推 [Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses)
（`POST /v1/responses`），定位是 Chat Completions 的继任者；OpenAI 明说 Chat Completions
「会继续长期支持」，但要下线的是老的 **Assistants API**（2026 上半年）。
新模型（gpt-5.x 那代）在 Responses 上能力更全：推理项、更好的工具调用、内建工具
（web_search / file_search / code_interpreter / image_generation / 远程 MCP）、服务端会话状态。

**已经定下的做法（用户 2026-09-15）**：**不做下游兼容层**，改成**在上游适配器里加一个协议选项**
—— 也就是和 `openai-compatible` / `anthropic` / `cloudflare-workers-ai` 并列的
`openai-responses`。客户端面继续只提供 `/v1/chat/completions`，谁的上游说 Responses
就给它挂这个适配器，翻译在这一层做。

**边界（先写清楚，免得以后误解）**：这个适配器只解决「**上游**说 Responses」。
**只认 Responses 的客户端**（新版 OpenAI SDK 默认、Codex CLI、Agents SDK 那类）打到我们这儿
仍然是 404（走 `src/app.js` 里那条"未实现该端点"的兜底），要另做一层下游的才算支持 —— 那是另一件事。

**要做的事（翻译清单）**：
- 请求：`messages` → `input`（items）+ `instructions`（system 提出来）；
  `max_tokens` → `max_output_tokens`；`response_format` → `text.format`；没有 `n`
- 响应：`output`（items）→ `choices[].message`；`output_text` → `content`；
  `usage` 形状不同（input/output tokens 加明细）
- 流式：**命名事件**（`response.output_text.delta` / `response.completed` …）→ 现有的 OpenAI chunk 形状，
  收尾照样发 `[DONE]`
- 工具调用：Responses 的 schema 更扁、**默认 strict**、调用结果是 `function_call` / `function_call_output`
  两种独立 item；要翻成 chat completions 的 `tool_calls` / `role: tool`（两边对应关系见官方「function calling」指南）
- **一定带 `store: false`**：默认会在上游留 30 天会话状态，我们这边是无状态的聚合网关，别替用户留痕迹
- 参考：上面那条迁移指南；差异的通俗版 <https://dev.to/dev-in-progress/chat-completions-vs-openai-responses-api-what-actually-changed-4bco>；
  Simon Willison 的解读 <https://simonwillison.net/2025/Mar/11/responses-vs-chat-completions>

**像谁**：工作量比 `anthropic` 适配器小一点（形状更像 OpenAI 自己），但流式事件和工具 item 是新的。

## ✅ 已修（2026-09-15）· 首次设置页：自动生成的下游 apikey 被说成"沿用原来的"

> **已修**：`/setup` 现在回三值 `accessKeyAction`（`changed` / `kept` / `generated`），
> 前端按值给文案 —— 留空且库里本来没有时会明说「已自动生成一条」。
> 旧的 `accessKeyChanged` 保留（兼容别的调用方）。下面留档原始记录。
>
> ⚠ 教训：修完之后要在 `docs/待办.md` 里标掉 —— 用户有一次按"文档说修了"去查代码，
> 发现其实没修（那条一直挂着"待修"）。

**现象**：全新部署第一次进 `/admin`，首次设置页的「下游 apikey」留空提交 → 后端自动生成了一条，
但弹窗写的是「下游 apikey **沿用原来的**：`sk-agg-…`」。库里本来一条都没有，"沿用"是错的。

**严重程度：纯文案，key 没丢。**
返回的就是新生成那条的明文（`result.accessKey`），还自动复制进剪贴板了 ——
用户拿得到、能直接用。问题只是措辞会让人怀疑"我是不是没设置成功／它偷偷保留了别人的 key"。

**位置**
- `public/app.js:383` —— `const kept = !result.accessKeyChanged;`，第 389 行按这个布尔二选一给文案
- `src/admin/routes.js:161-169` —— `/setup` 里的 `accessKeyChanged` 只在"用户自己填了口令"时为 `true`；
  留空时，无论"沿用旧口令"还是"新建一条"，都是 `false`

**根因**：后端只回一个布尔，把两件不同的事混成了同一个 `false`：

1. 留空 + 库里已有口令 → 沿用（真的沿用了）
2. 留空 + 库里没有 → 新生成一条（跟"沿用"没有任何关系）

**修法（建议）**：把那个布尔换成三值 `accessKeyAction`，前端按值给文案，一次说清：

| 值 | 什么情况 | 文案 |
|---|---|---|
| `changed` | 用户填了口令 | 新的下游请求 apikey：… |
| `kept` | 留空 + 原本就有 | 沿用原来的：… |
| `generated` | 留空 + 原本没有 | 已自动生成一条：… |

`else` 分支里看 `primary()` 是不是 `null` 就能区分，不用多查一次库。
`accessKeyChanged` 建议保留（别的调用方可能在看），只是前端改用新字段。

**顺带看一眼的两处（同一段代码，先没动）**
- `public/app.js:376`：`keeps` 为真（已有口令）时，用户点了「更改」但没填内容 →
  前端会自己 `randomAccessKey()` 塞一条发过去（而不是留空）。行为上等于"点了更改就换一条"，
  可以接受，但没有二次确认文案。
- 前端第 395 行那句「沿用原来的（`sk-****`）—— 这条是早期版本建的，看不到明文」
  只在密文解不开（`APP_SECRET` 换过）时才会走到，正常情况碰不到。
