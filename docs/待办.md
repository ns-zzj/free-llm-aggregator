## 2026-09-15 · 首次设置页：自动生成的下游 apikey 被说成"沿用原来的" ✅已记录，待修

**现象**：全新部署第一次进 `/admin`，首次设置页的「下游 apikey」留空提交 → 后端自动生成了一条，
但弹窗写的是「下游 apikey **沿用原来的**：`sk-agg-…`」。库里本来一条都没有，"沿用"是错的。

**严重程度：纯文案，key 没丢。**
返回的就是新生成那条的明文（`result.accessKey`），还自动复制进剪贴板了 ——
用户拿得到、能直接用。问题只是措辞会让人怀疑"我是不是没设置成功／它偷偷保留了别人的 key"。

**位置**
- `public/app.js:383` —— `const kept = !result.accessKeyChanged;`，第 389 行按这个布尔二选一给文案
- `src/admin/routes.js:161-169` —— `/setup` 里的 `accessKeyChanged` 只在"用户自己填了口令"时为 `true`；
  留空时，无论"沿用旧口令"还是"新建一条"，都是 `false`

**根因**：后端只回一个布尔，把两件不同的事混成了同一个 `false`：

1. 留空 + 库里已有口令 → 沿用（真的沿用了）
2. 留空 + 库里没有 → 新生成一条（跟"沿用"没有任何关系）

**修法（建议）**：把那个布尔换成三值 `accessKeyAction`，前端按值给文案，一次说清：

| 值 | 什么情况 | 文案 |
|---|---|---|
| `changed` | 用户填了口令 | 新的下游请求 apikey：… |
| `kept` | 留空 + 原本就有 | 沿用原来的：… |
| `generated` | 留空 + 原本没有 | 已自动生成一条：… |

`else` 分支里看 `primary()` 是不是 `null` 就能区分，不用多查一次库。
`accessKeyChanged` 建议保留（别的调用方可能在看），只是前端改用新字段。

**顺带看一眼的两处（同一段代码，先没动）**
- `public/app.js:376`：`keeps` 为真（已有口令）时，用户点了「更改」但没填内容 →
  前端会自己 `randomAccessKey()` 塞一条发过去（而不是留空）。行为上等于"点了更改就换一条"，
  可以接受，但没有二次确认文案。
- 前端第 395 行那句「沿用原来的（`sk-****`）—— 这条是早期版本建的，看不到明文」
  只在密文解不开（`APP_SECRET` 换过）时才会走到，正常情况碰不到。
